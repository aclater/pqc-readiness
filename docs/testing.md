# How pqc-readiness is tested

A readiness scanner is only useful if its answers are right on the hosts
people actually run. Testing is built around that: probes are tested against
data captured from real systems, every output format is validated against its
official schema, and the scanner is run end to end on booted distributions
before probe changes merge.

Testing has five layers, from fastest to most realistic.

| Layer | What it proves | Where | When |
| --- | --- | --- | --- |
| [Unit and fixture tests](#unit-and-fixture-tests) | Each probe and parser gets the right answer from real-system data | `tests/` | Every PR and push |
| [Output contracts](#output-contracts) | Every format validates against its official schema; JSON output does not change by accident | `tests/` | Every PR and push |
| [Distribution containers](#distribution-containers) | The suite passes under each distribution's own Python, OpenSSL and OpenSSH | `.github/workflows/` | Every PR (UBI 8, UBI 10, Debian); weekly (Tier 2) |
| [Booted VM matrix](#booted-vm-matrix) | The scanner gives correct results on a real booted host of each distribution | Maintainer KVM host | Before merging probe changes; before releases |
| [Release verification](#release-verification) | The published file is the one that was tested | Release PR | Every release |

## Unit and fixture tests

The suite (`pytest tests/`) needs only the standard library and runs as an
ordinary user. Probe tests read a fixture host root instead of `/`; a small
set of smoke tests also runs the scanner as a subprocess on the test machine
itself, to check exit codes, flag handling and the launcher.

**Fixtures come from real systems.** Each directory under
[`tests/fixtures/`](../tests/fixtures/) that holds captured data has a README
recording where it came from: the cloud image or container (checked against
the publisher's SHA-256), the date, and how it was captured. Examples:

- crypto-policies back-ends and `openssl.cnf` trees from booted EL9, EL10,
  Fedora and SUSE images, so the "is PQC actually enabled" logic is tested
  against what each distribution really ships;
- rpm databases in all three formats (SQLite, Berkeley DB, ndb) from real
  images, so the in-process readers are tested against the formats in the
  field;
- package-signing keys, including RHEL 10's hybrid ML-DSA-87+Ed448 release
  key;
- `sshd -T` output, `/proc/cpuinfo` flags (Skylake-X, Sapphire Rapids, Zen 4,
  Graviton 3), s390x `lszcrypt` output, `openssl speed` output, and
  `os-release` files for every supported distribution;
- certificates generated by OpenSSL 3.5 with ML-DSA, SLH-DSA and composite
  keys, plus truncated and malformed DER, for the trust-store classifier.

**Expected values come from independent tools.** Where possible a test
asserts that the scanner matches the distribution's own tool on the same
data. For example, the rpm readers must return exactly the package list
`rpm -qa` printed in that image, and the signing-key inventory must match
`rpm -q gpg-pubkey`.

**Hardware the project cannot run on is tested by captured output only.**
HSMs, DPUs, s390x Crypto Express cards and network HSM appliances are covered
by fixtures of their tools' output, not by live hardware.

## Output contracts

- **Official schemas.** CycloneDX 1.6 and 1.7 CBOMs, SARIF 2.1.0, SPDX 3.0.1
  JSON-LD and OCSF 1.9.0 events are validated against the official schemas and
  contexts bundled under `tests/fixtures/`. The Dependency-Track compatibility
  mode is checked against an export recorded from a real Dependency-Track
  5.2.0 instance ([integration notes](integrations/dependency-track.md)).
- **Golden report.** `tests/fixtures/golden/stubbed-host-report.json` is the
  complete `--json` report of a stubbed host. Any change to the JSON output
  fails the suite until the golden file is regenerated on purpose
  (`make golden`), so schema changes are always deliberate and reviewed.
- **The zipapp matches the source.** CI builds `pqc-readiness.pyz` and runs the
  whole suite a second time against it (`PQC_READINESS_PYZ=...`), then runs the
  zipapp as an executable and parses its JSON.
- **Documentation is tested too.** CI fails if a `--help` flag is missing from
  the README (`scripts/check-readme-flags.sh`), if a SARIF rule has no help
  page or a page has no rule, if a top-level JSON field is undocumented, if the
  documented schema version is stale, or if the README's distribution-support
  table claims CI coverage that no workflow provides.
- **Static checks.** `ruff`, `mypy --strict`, `detect-secrets` and the
  pre-commit hooks run on every PR. A separate check rejects references to
  third-party products the project does not describe by name.

## Distribution containers

GitHub-hosted runners can't boot a VM per distribution, so CI runs the suite
inside each distribution's container image. That exercises the distribution's
own Python, OpenSSL and OpenSSH, but not a booted kernel.

| Workflow | Runs on | What it does |
| --- | --- | --- |
| `ci.yml` | Every PR and push | Lint, type check and the suite under CPython 3.11, 3.12 and 3.13; zipapp build and re-test; README flag check |
| `ci-ubi8.yml` | Every PR and push | Builds `Containerfile.ubi8` and runs the suite under AppStream `python3.9` in UBI 8 |
| `ci-containers.yml` | Every PR and push | Builds the UBI 10 and Debian images, smoke-tests them, and runs the suite inside each |
| `ci-openshift-manifests.yml` | Every PR and push | Validates the DaemonSet and overlays with kubeconform, runs posture tests (non-root, dropped capabilities, read-only mounts), and checks the services image's file capabilities at runtime |
| `ci-prometheus.yml` | Every PR and push | Renders `--prometheus` output and checks it with `promtool check metrics` |
| `ci-tier2-weekly.yml` | Mondays, or on demand | Runs the suite in the stock container image of each Tier 2 distribution (Fedora, Rocky and AlmaLinux 9 and 10, Debian 13, Ubuntu 26.04, SLES via SUSE BCI) |
| `release-images.yml` | Each published release, or on demand for a release tag | Builds the UBI 10, UBI 8, Debian and services images from the release's checksum-verified zipapp, runs the suite inside each, verifies the services image's file capabilities, then pushes, signs and attests them |

## Booted VM matrix

Containers don't have firmware, a kernel, systemd services or an sshd, so
every change to a probe is also run on booted cloud images before it merges.

- **Images.** Unmodified vendor cloud images, each verified against the
  publisher's SHA-256: RHEL-compatible EL8, EL9 and EL10 (Rocky, AlmaLinux,
  Oracle Linux, CentOS Stream), Fedora, Amazon Linux 2023, Ubuntu and openSUSE
  Leap and Tumbleweed. RHEL itself is tested from RHEL images where a
  subscription is available, and from UBI containers otherwise.
- **Boot.** Each image boots under QEMU/KVM with UEFI firmware (BIOS where an
  image needs it) and a cloud-init seed that runs the zipapp as root and
  writes the results to the serial console. Overlay disks keep the base images
  untouched.
- **What is checked.** The scanner's JSON and SARIF against what the
  distribution's own tools report on the same host (`rpm -qa`, `sshd -T`,
  `update-crypto-policies --show`, `openssl list`), plus the specific behaviour
  the change targets. A change that alters results is re-run on the whole
  matrix and the before and after outputs are compared.
- **Published results.** A full scan of the current release across the matrix
  is kept as [example output](examples/os-matrix-2026-10.md).

The FIPS-mode matrix (booted hosts with `fips=1`) runs separately in the
[`aclater/distro-matrix`](https://github.com/aclater/distro-matrix) runner.

## Release verification

A release PR is the only change that bumps `SCHEMA_VERSION`. Before it merges,
the JSON schema change is checked to be additive against the previous release
tag. After the release is published, the `pqc-readiness.pyz` and `.sha256`
release assets are downloaded, the checksum is verified, and the downloaded
file is run to confirm it reports the expected version and schema. The release images
are built from that same verified zipapp; their tags and digests are recorded
in the release's `container-images.txt`, and a test keeps the deploy manifests
pointing at the current release's image tag.

## What is not tested

- Live HSMs, DPUs, s390x hardware and network HSM appliances (captured output
  only, see above).
- A live multi-node OpenShift cluster, and ACM. The manifests are
  schema-validated and posture-tested in CI. They were deployed by hand on a
  single-node OpenShift 4.22 cluster with the Compliance Operator
  ([examples/openshift-4.22-live.md](examples/openshift-4.22-live.md)), but
  CI doesn't deploy them. The Kubernetes variants were deployed the same way on
  a Rancher-managed two-node RKE2 cluster
  ([examples/rancher-rke2-live.md](examples/rancher-rke2-live.md)).
- Integration recipes are marked with what was and wasn't run against the real
  product; see each page under [integrations/](integrations/).
- macOS support is best-effort and is not in CI.

## Running the tests

```bash
python3 -m pytest tests/ -q                     # the suite, against the source
make test-pyz                                   # the suite, against a fresh zipapp
bash scripts/check-readme-flags.sh              # README documents every flag
PQC_WRITE_GOLDEN=1 python3 -m pytest tests/test_main_decompose.py -q -k golden  # regenerate the golden report (intended JSON changes only)
```
